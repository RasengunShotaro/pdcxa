# 記号・表記ルール（詳細）

散文として書く。記号で構造をでっち上げると AI 臭が出る。SKILL.md の鉄則 2 を補足する。

## Markdown を使わない

- 太字 `**…**`、見出し `##`、箇条書き記号（`-` `*` `1.`）、水平線、装飾はすべて禁止
- 元の下書きが箇条書きでも、依頼が「散文として自然に」なら文に溶かす
- ただし元の文書構造を保つべきとき（手順書・仕様・項目が本質的に並列なリスト）は、構造そのものは残してよい。残す場合も各項目内の文を humanize する。判断に迷うなら散文化を優先する

## カギ括弧 `「」`

- 強調のための括り、定義っぽい括り（「重要」「効果的」のような）は消して文脈に溶かす
- 残してよいのは、引用・会話・固有の呼称・誤読を招く語の明示だけ。それも最小限
- 悪い例「このツールは「効率化」を実現します」→ 良い例「このツールで作業が速くなる」

## 丸括弧 `（）`

- 補足を括弧に逃がさない。必要なら本文の一文として組み込む
- 用語の説明は初出で一度だけ。可能なら括弧を使わず文で説明する
- 悪い例「API（外部連携の窓口）を叩く」→ 良い例「外部と連携するための API を叩く」。文脈で自明なら説明ごと省く

## コロン `：`

- 原則使わない
- 使う場合も直後に半角スペースを入れない。`： ` は禁止
- 「目的：…」「背景：…」「結論：…」のようなラベル列挙をしない。文で続ける

## スラッシュ `／`

- 概念を並列するのに使わない。「コスト／品質／速度」ではなく「コストと品質と速度」あるいは文で
- ファイルパスや日付など本来スラッシュを使う表記は対象外

## 矢印・疑似コード `→` `=>`

- 因果や遷移を矢印で表さない。「A → B」ではなく「A すると B になる」と文で書く
- UI のメニュー階層・操作経路を表す矢印（設定→保存）は別物。「A すると B になる」と機械適用すると意味が壊れる。経路は階層として文に開く。「設定の中の保存」「設定メニューから保存を選ぶ」のように書く。元の経路の意味を保つことを優先する

## 全角ダッシュ `——`

- 補足の挿入に使わない。読点で繋ぐか、文を分ける
- 悪い例「この手法——昨年導入したもの——は」→ 良い例「昨年導入したこの手法は」

## 締めの定型句

- 「参考になれば幸いです」「まずは小さく始めましょう」「ぜひお試しください」のような定型の締めを足さない
- 締めが必要なら、元文の内容に即した淡い一文にする
