# Dimension: テスト

担当は **テストの必要十分性と品質**。「このロジックのバグが将来出たとき、既存テストで検出できるか」「テスト自身が嘘をついていないか」を見る。プロダクションコードの正しさは correctness reviewer。

## 読む rules

- `.claude/rules/common/testing.md`
- `.claude/rules/typescript/testing.md` (深刻度の指針セクションまで全部。テスト品質規約の本体)
- `.claude/rules/react/testing.md` (frontend / story の diff のとき)

## 検出対象

### カバレッジの十分性
- 自分で書いたロジックにテストがあるか (ロジックがあるのにテスト無し = 未完了扱い)
- 純粋関数のテスト欠落
- エッジケースのテスト漏れ (空文字, 巨大値, 不正型, undefined, 境界値)
- 重要な振る舞いの漏れ (エラー時挙動, 失敗パス)
- **テナント / ユーザー越境拒絶のテスト欠落** (`testing.md` §11。多テナント機能では必須、欠落は深刻度 `[高]`)

### テスト品質 (存在するだけでは不十分)
- AAA パターン違反 / 1 テスト複数観点 (`testing.md` §1-2)
- 期待値に実装ロジック流出 (実装と同じ式を期待値に書く = 共犯テスト, §4)
- mock 必須テスト = 設計の悪臭 (`vi.fn()` で SDK 直接 mock, `as unknown as`, §5-6)
- 実装詳細テスト (内部呼び出し回数, 内部データ構造, タイミング, §7)
- 層間の重複テスト / 上位から到達不能な下位分岐の未テスト (§8)
- module スコープの mutable state, fixture 依存の assert (§9-10)

### テスト名 (readability reviewer と重複可、テスト固有の観点はこちらでも見る)
- `it` 名がドメイン語か (SDK / Web Standard / DOM 技術語の leak は §3)
- 単独で観点が読めるか (「〜も」「同じ」の前テスト依存名は NG)

## 検証手段

- テストが実際に通る/落ちることを `bun run test` で確認 (追加提案するテストは、現実装で意図通り pass/fail するか自分で書いて流す)
- 「このテストは実装が壊れても気付けるか」= 実装を 1 箇所わざと壊して (一時的に、検証後戻す)、テストが赤くなるか確認すると確実
- カバレッジ数値は追わない。振る舞いがテストされているかで判断

## AUTO_FIX / ESCALATE の寄せ方 (この dimension 固有)

- 純粋関数のテスト欠落 (入出力が一意), 明白な実装詳細テストの削除, テスト名の技術語リネームは **AUTO_FIX** 寄り
  - ただしテスト名の技術語 leak は **production 識別子側にも同じ語がある** ことが多い。テストだけ直すと production と乖離するので、production 側も直す前提で扱う (片方だけの修正なら ESCALATE で意図確認)
- 「この振る舞いをテストすべきか」の判断に仕様解釈が要る (エラー時にリトライか失敗か等) なら **ESCALATE**
- テスト削除 (実装詳細テストでも) は意図確認が要るので原則 **ESCALATE**
