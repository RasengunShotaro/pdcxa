# Dimension: 仕様 (振る舞い検証)

担当は **「実装が、ユーザーにとって期待される振る舞いになっているか」**。他の dimension がコードの内部品質を見るのに対し、ここは **外から見た振る舞いだけ** を見る。

**実装を読んで「正しそう」と推測で判断するのは禁止。** ユーザーがたどる動線をシミュレートし、**empirical に確定した振る舞い** で判断する。「このコードはこう動くはず」という願望ベースの推測は禁止。

ただし empirical = 本番実行とは限らない。**生成物を構築・観測して確定すれば empirical** (= 後述「検証手段」の rung 0。例: 生成 hook に invalidate があるか `grep`、生成型と消費側の突き合わせ)。実行 (test client / dev server / ブラウザ) が要る残差だけ Skipped に回す。**「ブラウザで動かせない」ことだけを理由に全部 Skipped に倒さない** — 静的に確定できることは確定させる。禁止なのは「ソースを読んで plausible だと感じた」レベルの推測であって、生成物を構築・grep した確定ではない。

## 大原則

1. **動線を先に言語化する**: この diff が触る機能について、ユーザーが踏む手順を 1 本のシナリオに書き下す (例: 「プロジェクト一覧 → 新規作成ボタン → フォーム入力 → 保存 → 一覧に反映される」)。手順の各ステップで「何が起きるべきか」を期待値として先に決める。
2. **本当にそのワークフローか疑う**: diff やコミットメッセージが主張する振る舞いを鵜呑みにしない。spec / plan ドキュメントがあっても「正解」視せず、実際の挙動と突き合わせる。主張と実挙動がズレていたらそれが最重要の指摘。
3. **振る舞いを観測する**: 実装の中身ではなく、入力 → 出力 / 画面遷移 / 永続化結果 を観測する。「別の実装に変えても同じ振る舞いなら OK」という基準で見る。

## 検証手段 (empirical 必須・優先順)

`review-contract.md`「検証の梯子」に従う。**生成物を自分で構築して観測できれば empirical**であり、必ずしも本番実行は要らない。安く・忠実な順に:

0. **静的構築で確定する (rung 0)**: 動線の成否が生成コード / 生成物から確定できるなら、それで empirical 確定し指摘に上げてよい (実行不要)。例: orval 生成 hook に cache invalidate があるか `grep`、レスポンス型と消費側の突き合わせ、状態遷移の分岐を読んで到達不能パスを特定。「読んで『ぽい』」は禁止だが、生成物を構築・grep して**確定**したものは AUTO_FIX/ESCALATE に上げてよい。**「動かしていない」ことだけを理由に Skipped に倒さない**。
1. **既存 / 追加の統合テスト・test client で動線を再現する**: API なら hono の test client / `app.request()` で動線通りにリクエストを並べ、レスポンスと永続化を観測。`bun run test` で流す
2. **CLI / curl で API を叩く**: ローカルで起動できるなら動線通りに叩いて応答を観測 (実 DB を破壊しない範囲)
3. **UI は dev server + playwright/chrome devtools で実機操作**: 該当ページに到達 → 主要操作 (form 送信 / mutation / navigation) を 1 周 → エラーケース (validation 失敗 / mutation 失敗) も観測。**MSW モードと実 backend モードで cookie / cache invalidate / 永続化反映の挙動が違う** ことに注意 (development-workflow.md)
4. どれも環境上できない (backend 未起動・実データ必須・外部依存) なら **Skipped** に回す。実装を読んだだけの推測を AUTO_FIX/ESCALATE に上げない

## 検出対象 (振る舞いのズレ)

- **動線が途中で壊れる**: あるステップで期待した遷移 / 反映が起きない (例: 保存したのに一覧に出ない, mutation 後に cache が invalidate されず古い表示)
- **主張と実挙動の乖離**: コミット / spec が「こう動く」と言っているのに、動かすと違う
- **エラー動線の欠落**: validation 失敗 / mutation 失敗 / 権限不足のときにユーザーが詰まる・無言で失敗する
- **状態遷移の誤り**: 期待した順序・条件で状態が遷移しない
- **境界の取りこぼし**: 空データ / 初回 / 権限違い / 別テナントでの動線が破綻する
- **API 契約のズレ**: レスポンス shape が orval 生成型 / フロント期待と食い違う (OpenAPI component の二重登録で型が壊れる類)

## AUTO_FIX / ESCALATE の寄せ方 (この dimension 固有)

- 動かして再現できた **明白な振る舞いの壊れ** (保存が反映されない等) で、修正方針が一意なら AUTO_FIX
- 「期待される振る舞いが何か」自体に解釈が要る (エラー時に無視/失敗/リトライのどれが正か, 状態遷移条件) なら **ESCALATE**。業務シナリオ + 起こる事象 + 判断ポイントの 3 段で書く
- 動線シミュレーションの結果、**そもそも要求された機能が未実装の BC に依存していて今は作れない** と判明したら ESCALATE (need が未実装依存)
