# Dimension: 可読性

担当は **次の作業者・ユーザーが読んだときの認知負荷**。コードが動くかではなく「読んで意味が正しく伝わるか」を見る。日本語としての自然さ、技術用語の漏れ、ラベルの妥当性が中心。実行検証は不要、規約と diff で判断する。

## 読む rules

- `.claude/rules/typescript/coding-style.md`「命名規律」セクション全部 (このdimensionの主軸)
- `.claude/rules/common/coding-style.md` (コメント方針, ユーザー向け文言の "LLM"→"AI")
- `.claude/rules/react/coding-style.md` (frontend の diff のとき)

## 検出対象

### 日本語識別子・テスト名の自然さ
- 関数名 / 型名 / テスト名の日本語が業務語として自然に読めるか。動詞句が entity 名詞に化けた曖昧名 (`書類取込` を entity として使う等) は flag
- ドメイン関数名に目的語が含まれるか (`プロジェクト配下を集計する` は何を集計か不明)
- 英語クラス名の機械的な訳語ではなく、PdM や現場担当者が読んで通じる業務語か
- テスト名 (`it`) がドメインの意味で書かれ、単独で観点が読めるか (技術語 leak / 前テスト依存名は NG)
- 数字接尾辞 `xxx1`/`xxx2` を並列概念以外に使っていないか

### 技術用語のフロント流出 (重要)
- **ユーザーの目に触れる文言 (画面 / 通知 / API エラー本文) に技術用語が出ていないか**
  - `"LLM"` → `"AI"` (ユーザー向けは AI 表記。内部識別子・型名・ログは対象外)
  - `Id` 接尾辞をそのままラベルに出していないか (「工種 ID」ではなくドメイン語「工種」)
  - SDK / クラウド製品名 / 内部実装語 (`status: extracting` 等) がユーザー文言に漏れていないか
- 他 BC と紛らわしい汎用ラベル (「ファイル取込」が複数 BC で重複) を BC 文脈に絞れているか

### コメント・ドキュメント方針
- **新規コメント / docstring / JSDoc は 0 を目指す**。意図はコード構造・命名・型で表現する。残してよいのは `common/coding-style.md` が挙げる 3 種 (定数の出所 / 外部仕様の癖 / 消すと壊れる分岐の前提) に当たり、かつ「消したら次の作業者がコードを壊すか」に Yes と言えるものだけ。
  - 変更ファイルの追加行を `grep -nE "^[[:space:]]*//|[^:/]//[^/]|/\*"` で全数洗い、URL / MSW パス文字列等を除いた `//`・`/* */`・JSDoc を 1 件ずつ判定する。3 種に当たらないものは AUTO_FIX (削除) に挙げる。
  - 「読みやすくなる」「判断の理由を書いた」は残す理由にならない。コードの再説明・検討の経緯・棄却した案は commit message / PR 本文に寄せる。
- 既存コメントの削除は、今回触る箇所でなければ不要

### 一般可読性
- 命名の弱さ (意図が読めない変数名), 略語の濫用
- マジックナンバー / マジックストリングが定数化されず読み手に意味が伝わらない

## 判定の指針

- 「識別子・entity ラベル」(型名 / フィールド名 / モノを指す UI ラベル) が対象。サイドバー・タブの **機能/メニュー名** は対象外 (`書類取込` のような動詞句のままで OK)
- 迷ったら `typescript/coding-style.md`「日本語識別子は自然な業務語にする」の判定基準に従う

## AUTO_FIX / ESCALATE の寄せ方 (この dimension 固有)

- 命名 cleanup / 追加コメント削除 / マジックナンバーの定数化 / テスト名の技術語リネームは **AUTO_FIX** 寄り (mechanical)
- **ユーザー向け文言** (画面・通知・ラベルの文言) の変更は、たとえ技術語漏れでも **ESCALATE** (ドメイン語の選択にユーザーの意図が要る。`review-contract.md`「ユーザー向け文言」)
- production 識別子のリネームが広範囲に波及する (公開型 / 共有 component) なら ESCALATE
