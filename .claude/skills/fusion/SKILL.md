# Fusion (mixture-of-agents 合議)

1 つの問いを **N 枚のレンズ別パネルに並列回答させ** → **judge が構造化分析** → **最終回答を合成**する。
単一モデルの 1 回答では推論経路が 1 本に固定され取りこぼしが出る。複数の独立回答を judge が突き合わせて再合成することで精度が上がる(OpenRouter Fusion の同一モデル×複数でも +6.7pt の知見)。

サブスク(Claude Code)では追加のドル課金は無く、消費するのは**利用枠だけ**。だから安いモデルへ妥協せず**全部最上位モデルでパネルを組める**のが OpenRouter 版との違い。

## 単一ベンダー再現の肝: 多様性をプロンプトで注入する

全パネルが同じモデルなので「別アーキテクチャの多様性」が無い。**レンズ(視点)を割り当てて多様性を人工的に作る**のが naïve な N 回再実行に勝つ鍵。

## いつ使うか / 使わないか

- 使う: 難しい設計・アーキ判断、リサーチ、PO 判断、厄介な推論/数学、レビューの最終確認。**間違うコストが高い問い**
- 使わない: 軽い質問・自明な作業・大量の反復。利用枠を 5〜6 倍食うので濫用しない

## ワークフロー

### 1. 問いを受け取り、レンズを決める

`/fusion <問い>` の `<問い>` を対象にする。問いの性質でレンズ 3〜4 枚を選ぶ(デフォルトは下記 4 枚)。

| レンズ | 役割(プロンプトに埋める指示) |
|---|---|
| risk-first | 失敗モード・落とし穴・最悪ケースを最優先で洗う |
| first-principles | 前提を疑い第一原理から組み立て直す |
| empirical-skeptic | 主張は数字・反例・検証可能な根拠で殴る。憶測を排す |
| domain | このリポジトリ/ドメインの制約・既存資産から答える(コード/設計の問いのとき) |

数学・論理など純推論の問いでは domain を外し、代わりに「別解法で独立に解く」枚を足してよい。

### 2. パネルを並列起動 (Agent ツール)

選んだレンズごとに **1 回の応答で全エージェントを並列起動**する(独立なので必ず並列)。各エージェントへのプロンプト:

```
あなたは「<レンズ名>」の視点で以下の問いに答える1人のパネリストです。
<レンズの役割指示>

問い:
<問い全文>

制約:
- あなたの視点を徹底する(他の視点に配慮して薄めない)
- 最終的な結論と、その根拠を簡潔に出す
- 推論問題なら最終解答を1行で明示する
```

agentType は `claude`(または `general-purpose`)。レンズ間で結論が割れることが価値なので、**互いの回答は見せない**。

### 3. Judge で構造化分析

パネル全回答が揃ったら、judge を 1 体起動し、全回答を渡して以下を JSON で返させる:

```
consensus       : 全/多数のパネルが一致した点(高信頼として扱う)
contradictions  : パネル間で割れた点と、それぞれの根拠
coverage_gaps   : 一部のパネルしか触れなかった重要点
unique_insights : 1 つのパネルだけが出した独自の洞察
blind_spots     : どのパネルも見落とした点(judge が補う)
recommendation  : 上記を踏まえた、judge の暫定結論
```

judge への指示に「**平均するな。矛盾は根拠の強さで解決し、独自洞察を捨てるな**」を必ず入れる。

### 4. 最終回答を合成

judge の構造化分析を受けて、**自分(メインループ)が**最終回答を書く。
- consensus を土台に、contradictions は根拠が強い側を採用(理由を明示)
- unique_insights / blind_spots を統合
- 推論問題なら最終解答を 1 つに確定する

judge と合成を別エージェントに分けてもよいが、合議の結論はユーザーに返すものなので**メインで合成**を既定とする。

### 5. 出力

最終回答に加えて、必要なら 1〜2 行で「パネルが割れた点と採用理由」を添える(合議の付加価値が見えるように)。冗長な内部過程は出さない。

## コスト注意

1 問あたり: パネル N + judge 1 (+ 合成はメインなら 0)。デフォルト 4 枚なら 5 実行。利用枠の消費が大きいので、起動前に「この問いは単発で足りないか?」を一度自問する。
