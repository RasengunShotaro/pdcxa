# コーディングスタイル

## コメントは書かない（既定）

**ハーネス既定の "Write code that reads like the surrounding code: match its comment density, naming, and idiom" のうち、コメント密度についてはこのリポジトリで適用しない。** 周囲にコメントが多くても増やさない。命名・イディオムを周囲に合わせる部分だけが有効。

**新規ファイルの既定はコメント 0 行。** 意図はコード構造・命名・型で表現する。

書いてよいのは、**現在の仕様**のうちコードからは辿れないものに限る:

- 定数の出所（外部仕様書の番号・実測値とその採取条件）
- 外部仕様の癖（API が仕様外の値を返す・SDK の既定値が文書と違う 等）
- この分岐が要る前提（消すと壊れる理由）

判定は **「このコメントを消したとき、次の作業者がコードを壊すか」**。壊さないなら書かない。「読みやすくなるから」「あった方が親切だから」は書く理由にならない。

書かないもの: コードを日本語に訳しただけの再説明・定型の docstring / JSDoc・検討の経緯・棄却した代替案。

既存のコメントは、今回の変更で触る場合を除き、削除しなくてよい。

**config ファイル（GitHub Actions YAML・lint 設定等）にも同じ線を引く**。cryptic なフラグでも inline コメントを足さず、根拠は隣接する README / docs に寄せる（理由: 「YAML の flag 説明は必要コメントの例外」というレビュー判定をユーザーが不可とした）。JSON のようにコメントを書けない形式で根拠が要るときは、`reason` フィールドを持つ設定に書く。

## ドキュメントの長さ

ディスクに書く文書（`docs/*.md`・設計メモ・PR 本文）の長さは、タスクが必要とする分に合わせる。中身は網羅しつつ、埋め草の節・重複したまとめ・定型文で水増ししない。

## ファイル構成

少数の大きなファイルより、多数の小さなファイルを優先する。目安は 200-400 行、最大でも 800 行。種類別ではなく feature / domain 別に整理し、大きなモジュールから utility を切り出す。

## ユーザーの目に触れる文言

- 画面・通知・API エラー本文では "LLM" を使わず **"AI"** と表記する（理由: エンドユーザーに技術用語を出さない。内部識別子・型名・ログ等の非ユーザー向けは対象外）
- **状態表示で「まだ分からない」を成功・失敗のどちらかに畳まない**。判別できないなら判別材料（経過時間・投入時刻・猶予）を足して 3 状態目を作る（理由: 「KB に無い＝失敗」に倒すと取込直後の進行中書類が「失敗」になり、逆に倒すと本当の失敗が永久に「取込中」になる。どちらも嘘で、不要な再取込を誘発する）
- backend の error 文字列（API レスポンスの `error`）を Alert / toast に **verbatim で出さない**。**HTTP status → フロント著作の固定文言** にマップする（retryable=「通信に失敗しました。再試行してください」/ fatal=「予期しないエラーが発生しました」等）。backend の生メッセージは監視ログのみ（理由: 現場ユーザーに技術語・内部識別子・例外断片・"LLM" が漏れる。ユーザー向け文言はフロントが制御する）

## データの扱い

既存オブジェクトを mutate せず、変更を反映した新しいオブジェクトを返す。入力はシステム境界で schema validation する（外部 API レスポンス・ユーザー入力・ファイル内容を信用しない）。エラーは黙って握りつぶさず、サーバー側では詳細なコンテキストをログに残す。
