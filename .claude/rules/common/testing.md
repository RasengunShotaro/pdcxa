# Testing Requirements

## 自分で書いたロジックにはテストを書く（最重要）

**ロジックがあるならテストを書く。テストの無い実装は完了とみなさない。**

- バグ修正時は、まず再現テストを書いてから修正する（RED → GREEN）
- テストフレームワークが未導入のworkspaceでは、最初に導入してから実装する
- セッション終了前に Stop hook (`.claude/hooks/check-test-pair.sh`) が警告を出す。要確認だが強制ではない

立ち上げ期からこの習慣を作る。後から「テスト書いてないコード」を遡って書くのは10倍重い。

## テスト不要なケース（例外）

「**自分で書いたロジックがあるか**」が判断基準。下記は省略可:

- **フレームワーク規約ファイル**: ボイラープレート的な規約ファイル（言語/フレームワーク固有）は E2E に任せる。具体例は各言語の rules を参照
- **外部 API/SDK の薄いラッパー**: 引数をそのまま渡すだけの関数は、実 API を叩く価値しかない（mock テストは無意味）。本質ロジックを pure function に切り出して、そちらをテストする
- **サードパーティコピペ**: upstream のテストを信頼する
- **純粋な型定義 / 定数のみのファイル**

迷ったら「**この関数のバグが出たとき、テストで検出できるか**」を考える。検出できないなら書いても無駄。

## カバレッジ

数値目標は追わない。**振る舞いがテストされているか**を重視する。
5割以下なら何か問題があると考える程度。

## Test Types

プロジェクトに応じて以下を使い分ける:

1. **Unit Tests** - ドメインロジック、ユーティリティ
2. **Integration Tests** - API エンドポイント、データベース操作
3. **E2E Tests** - Playwright による重要なユーザーフロー

## Troubleshooting Test Failures

1. テストの隔離性を確認
2. モックが正しいか検証
3. **テストではなく実装を修正する**（テストが間違っている場合を除く）
